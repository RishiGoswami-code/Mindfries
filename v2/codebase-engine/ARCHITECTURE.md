# Codebase engine — architecture

The redesigned engine for V2. It replaces "generate a mini-codebase per
candidate" with "**select** one of a few owned products and **generate a
role+JD task against it**, cached by the JD." Coverage rationale is in
[`ANALYSIS.md`](ANALYSIS.md); build order in [`PLAN.md`](PLAN.md).

Target surface: **V2** (`v2/api`, `v2/db`, the V2 Task/bundle service). V1
stays as it is. This slots into V2's existing substrate — versioned,
signed task bundles over `/session/bundle` ([`../contracts/cli-api.yaml`](../contracts/cli-api.yaml))
and the Task Service the spec already describes as "task versions, task files,
role-specific variants" ([SPEC §6](../SPEC.md)).

## The shift, in one line

```
BEFORE (V1):  invite → GenerateTask(role brief) → whole 4–7 file codebase + solution + verify   (per candidate, ~6 min, no cache)
AFTER  (V2):  select product (role+JD) → generate TASK against fixed product, cache by JD hash → serve product@commit + task overlay
```

Codebases are authored **once** and owned. Tasks are generated **once per
(product, role, JD)** and reused across every candidate on that JD. Nothing is
regenerated per candidate; a company editing the JD is the only thing that
invalidates a cached task.

## Four parts

```
                        role + JD (from the company portal, engine=v2)
                                        |
                                        v
   (1) Product registry  ───────►  (2) Selector  ──►  product @ golden_commit
   owned, versioned,                role→candidate            |
   test-green products              products, JD              v
                                    refines the pick   (3) Task engine  ──► task (brief + acceptance
                                                        generate-once,          tests + optional planted bug
                                                        cache by JD hash,       + reference solution), verified
                                                        variant pool            |
                                                                                v
                                                        (4) Delivery: V2 Task/bundle service
                                                        serve product archive @ commit + task overlay;
                                                        CLI clones/unpacks, TASK.md locked
```

## (1) Product registry — owned, verified codebases

Why owned and generated by us, not forked from OSS: **we must be able to
verify feature-addition and debugging tasks.** That requires a trusted test
suite and a known ground-truth (reference solution / known bug), which an
arbitrary OSS repo does not give us. So each product is source we author and
maintain, pinned at a **golden commit** where:

- the full test suite is **green**, it typechecks and builds (CI-gated);
- there is a **role-coverage manifest** (below);
- a set of **reference tasks** exist, each with its verified solution.

How a product is built correctly (this is the hard part the OSS route can't
give us) — see [`PLAN.md`](PLAN.md) Phase 1 for the pipeline. In short: author
it in pieces (scaffold → subsystem → tests), never one giant LLM call; harden
until the suite is green; human-review; freeze as the golden commit. The
suite *is* the correctness contract thereafter.

### `products` (new, `v2` schema)

| column | meaning |
|---|---|
| `id`, `slug`, `name`, `domain` | identity (e.g. `p1-support-saas`) |
| `repo_ref` | where the source lives (a V2-owned git repo / object store) |
| `golden_commit` | the pinned, test-green commit tasks are cut from |
| `stack` | languages/runtimes (feeds CLI preflight `required_runtimes`) |
| `role_coverage` | jsonb: `role → { subsystems:[paths], competencies:[...], modes:[...] }` |
| `status` | `draft` / `verified` / `retired` |
| `version` | bumped when the golden commit changes |

### The role-coverage manifest

The manifest is what makes selection and honest reporting possible. Per role it
names the **subsystems/paths** that role works in, the **competencies**
([SPEC §7 modes](../SPEC.md)) each area can exercise, and which it *cannot* —
so the report marks "not assessed" truthfully. It also bounds the context the
task engine is allowed to see (part 3), which is what keeps generation cheap
and non-truncating.

## (2) Selector — pick a product, don't generate one

Input: `role` + `JD`. Output: `product_id` + `golden_commit`.

1. Filter to products whose `role_coverage` includes the role.
2. Among those, rank by JD similarity to each product's domain/manifest text
   (embedding cosine + keyword tags: e.g. "payments/ledger/settlement" → P4,
   "tickets/support/helpdesk" → P1, "retrieval/agent/eval" → P2).
3. Pick the top product; record the score for audit.

Deterministic and cached per (role, JD hash). With 5 products this is mostly
role→product with the JD disambiguating the roles that two products serve.
Near-zero cost; no LLM codebase generation ever happens here.

## (3) Task engine — generate a task against a fixed product, cache by JD

A task is **a work item on the product**, not a codebase. Three families, each
with a deterministic check because we own the product:

- **Feature addition** — "implement X in subsystem S." We author the reference
  solution branch and its **acceptance tests**; the candidate's branch is
  verified by running those tests + the existing suite. We *know* it's
  reachable because we built the reference.
- **Debugging / reliability** — start from the golden (green) commit, apply a
  **planted-bug diff** that makes specific tests fail in a known way. The fix
  is the known reverse. Verified by: the failing tests go green, nothing else
  breaks.
- **Comprehension / review / design** — a prompt grounded in real subsystem
  code; evidence is review notes / a design artifact, scored by rubric.

### Cache key and regeneration (the Q4 decision)

```
task cache key = (product_id, golden_commit, role, jd_hash)
jd_hash        = hash(normalized JD text)
```

- On invite: if a task exists for the key → **reuse it** (no LLM call).
- If not → generate once, verify, store.
- **Company edits the JD → `jd_hash` changes → cache miss → regenerate.**
  In-flight candidates keep their pinned `task_version`; only new invites get
  the new task.

To avoid every candidate on one JD getting the identical task (integrity /
[SPEC §11](../SPEC.md) variants), each key holds a **small pool of calibrated
variants** (N configurable, default 3), generated once per JD and drawn
round-robin per candidate. The pool — not per-candidate generation — is the
unit of work, so cost stays flat in candidate count.

### Why generation is now cheap and won't truncate

The LLM authors only a **bounded diff + brief + tests** for one subsystem, not
a whole project. Context = just the manifest-named subsystem for the role
(retrieved by path), well under the token budget that bites the V1 engine
today. The product, tests, and history already exist around it.

### `product_tasks` (new, `v2` schema — the task bank + cache)

| column | meaning |
|---|---|
| `id`, `product_id`, `golden_commit` | which product/commit this cuts from |
| `role`, `jd_hash`, `variant_no` | the cache key + variant within the pool |
| `task_version` | stable id a running session pins to |
| `kind` | `feature` / `debug` / `review` / `design` |
| `brief_md` | the candidate-facing `TASK.md` |
| `overlay_ref` | task-specific files applied over the product (incl. planted bug for `debug`) |
| `acceptance_ref` | hidden acceptance tests (never shipped to the candidate) |
| `solution_ref` | reference solution branch (for verification + rubric calibration) |
| `verification` | jsonb: last verify run (pass/fail, which tests) |
| `rubric_ref` | the role rubric this task is calibrated against |

`game_templates` in V1 is the conceptual ancestor; here the heavy content
(starter/solution files) is replaced by references to a product + commit +
overlay, so a task row is tiny.

## (4) Delivery — reuse the V2 bundle/Task service

A V2 **Task** becomes `product_id + golden_commit + product_task_id`. Two
delivery shapes, both already anticipated by [SPEC step 7](../SPEC.md)
("CLI downloads/clones the assessment repository or creates a clean
workspace"):

- **Clone** the product repo at `golden_commit`, then apply the task overlay
  (writes `TASK.md`, any feature stub or planted-bug diff) on an assessment
  branch — the realistic default for large products.
- **Bundle**: for smaller products, the existing signed-tar `/session/bundle`
  path serves `product@commit + overlay` as today.

Either way `TASK.md` is locked and the manifest/hash integrity from
[`../contracts/cli-api.yaml`](../contracts/cli-api.yaml) is unchanged.
Submission verification runs the product suite + the task's `acceptance_ref`
against the candidate branch — a real, deterministic check, not a
regenerate-and-hope.

## Where the code lives

| Piece | Home | Note |
|---|---|---|
| `products`, `product_tasks` schema | `v2/db` | own migrations, `v2` schema |
| Selector + task engine | `v2/api` | the Task/Adaptive-Task service ([SPEC §6](../SPEC.md)) |
| Model calls | `v2/api` | server-side only (SPEC); copy a thin LLM client, own it, per the [V2 no-V1-import rule](../PLAN.md) |
| Product repos | V2-owned git/object store | referenced by `repo_ref` + `golden_commit` |
| Delivery | existing V2 bundle/Task service + CLI | extend, don't replace |

## Integrity, calibration, failure

- **Integrity:** real product history + per-candidate branches + a variant pool
  make copy/paste and cross-candidate sharing weaker; the CLI's coding-agent
  signals ([PLAN task 1.8](../PLAN.md)) still apply.
- **Calibration:** because every task ships a reference solution, the rubric is
  calibrated against a known-good run ([SPEC §14](../SPEC.md)), and the
  recruiter dry-run ([SPEC §7.5](../SPEC.md)) replays it.
- **Failure:** generation failure no longer strands a candidate — the pool
  already holds verified variants; a missing pool falls back to the product's
  bundled **reference tasks**. No alert-email dead-end like V1.

## What this buys, against the objectives

| Objective | How |
|---|---|
| Minimize repeated generation | No codebase generation; tasks generated once per JD, pooled, reused across candidates |
| Realism | Large, owned, test-green products with real history |
| Role coverage | 5 products × role-coverage manifests → all 8 roles (ANALYSIS matrix) |
| Scalability | Static product repos + cached task pools; cost flat in candidate count |
| Quality | Deterministic verification via owned reference solutions / planted bugs |
